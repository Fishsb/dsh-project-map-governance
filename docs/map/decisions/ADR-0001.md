# ADR-0001：薄契约层架构：插件仓库只含工具注册，引擎随 skill 目录独立演进

> 状态：accepted ｜ proposed ｜ deprecated ｜ superseded（当前：accepted）

## 背景

DSH 治理能力最初以 skill 目录内 `scripts/*.mjs` 引擎形式存在（Node 标准库，零依赖），供 pre-commit hook 与本机 CLI 使用。要让治理命令在 Harness 会话中以**原生工具**出现，需要一层 Cordis/schemastery 注册的插件。若把引擎复制进插件仓库，会出现双份实现漂移（hook 用 skill 版、插件用仓库版，行为不一致）。

## 决策

本仓库（`@dsh-external/project-map-governance`）只做**插件薄契约**：`src/index.ts` 把 skill 目录引擎的 6 个命令（init/sync/check/adr/status/reconcile）注册为 DSH 原生工具（`_dsh_external_project_map_governance_*`），参数 schema + `check --json` 结构化返回。引擎（规则/解析/命令实现）保持单一事实源，随 skill 目录独立演进；hook / CLI / DSH 插件 / MCP 四方共用同一引擎。引擎位置默认 `C:/Users/lk/.dsh/skills/project-map-governance/scripts`，可在插件 Config 中覆写。

## 后果

正面：单一事实源，无行为分叉；插件发布节奏与引擎解耦（引擎演进不必触发插件发版）。成本：插件脱离 skill 目录环境不可独立运行；本仓库 `scripts/build.sh` 是仓库自身构建脚本，易与引擎命令目录混淆（README 已注明）。

## 替代方案

- **引擎并入插件仓库**：双份实现漂移风险高，否决。
- **插件直接内联实现规则**：与 hook/CLI 行为分叉，且违反零重复原则，否决。
- **MCP 作为唯一集成面**：Harness 会话内仍需原生工具体验，MCP 仅作补充形态保留。
